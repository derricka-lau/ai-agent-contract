# Global Contract

## Mission
- Make safe, minimal, well-validated changes preserving architecture, behaviour, and maintainability unless broader change is requested.
- Treat AI output as a proposal for human judgement; surface decisions, risks, and tests before implementation.

## Standard Workflow
1. Understand task, constraints, nearby files, call sites, tests, and scripts before editing.
2. Produce a short plan beyond a trivial one-file change.
3. Keep dependent planning, implementation, and verification in one main loop; use subagents only for independent parallel work or justified context isolation (see `workflow.md`).
4. Locate or add the smallest failing automated test for the requested behaviour and present the test case or no-test rationale for review before implementation.
5. Implement the smallest change that solves the problem and makes the focused test pass.
6. Validate in order where available: targeted failing test -> focused re-run -> format -> lint -> type-check -> broader tests -> build.
7. Summarise changed files, commands run, risks, and unrun checks.

## Change Policy
- Reuse existing patterns and abstractions; avoid speculative refactors and unrelated edits.
- Do not implement behaviour changes before the relevant failing or missing automated test has been identified for review, unless the user explicitly approves a no-test path.
- Tests are not append-only. Prefer updating or replacing the nearest existing behavioural test before adding another. Remove superseded tests, fixtures, and helpers in the same change. Do not retain negative legacy-absence or source-text assertions unless absence is itself a security, compatibility, or public-contract requirement. The final test surface must describe current behaviour, not implementation history.
- Preserve the existing regression baseline until the replacement behavioural test exists and has failed for the intended reason; remove or rewrite superseded tests only after the replacement behaviour passes.
- Do not silently change public APIs, schemas, migrations, environment variables, generated artefacts, or tool configuration.

## Simplicity, Root Cause, And Cost
- Choose the simplest design satisfying correctness, security, compatibility, and testability; remove superseded code, dependencies, config, and docs in the same bounded change.
- Consider total engineering and operating cost (implementation, review, maintenance, migration, CI, runtime, model/API, network, storage) and surface material recurring or irreversible costs before implementation.
- Fix the verified root cause directly. Do not ship coding workarounds, hacks, silent fallbacks, compatibility shims, duplicated special cases, or blanket suppressions (`@phpstan-ignore`, `# type: ignore`, `// @ts-ignore`). If blocked, stop and surface the blocker.

## Quality Order
1. Correctness -> 2. Security -> 3. Compatibility -> 4. Test coverage -> 5. Maintainability -> 6. Performance where it matters.

## Standards, Architecture, And Precedence
- Match local conventions, prefer strict types and framework-native patterns, respect dependency direction, and use British English in user-facing text and docs.
- Keep one authoritative source for each rule, value, schema, or behaviour; generate or reference derived forms rather than duplicating policy. Generated and installed files are outputs, never competing sources of truth.
- Verify external or version-sensitive assumptions and framework APIs against official primary sources or local code during planning; never trust generated guides at face value, and state plainly when a claim cannot be verified.
- On conflict, follow platform/security constraints first, then the most specific source; the latest applicable, explicitly approved decision supersedes older task-local guidance. Update superseded sources and docs once implementation stabilises.

## Dependencies And Git Discipline
- Do not add dependencies without explicit approval; use lock-file packages, pin versions unless the repo differs, and run audits when dependencies change.
- Structure work as small, independently reviewable commits with one purpose each; do not commit unless authorised, and never amend published commits or force-push protected branches unless requested.
- Use Conventional Commits (`type(optional-scope): concise imperative summary`, ≤72 chars, no trailing period) and explain *why* in the body when non-obvious.
- Never include `Co-authored-by:` trailers, `Generated with`/`Generated by`/`Assisted-by:` footers, or any AI/tool attribution in commits or PR descriptions.
- Never commit secrets, `.env` files, local config, credentials, or private artefacts.

## Scope And Output
- One task, one focus; mention out-of-scope improvements afterwards.
- Lead with the answer or action, state assumptions, validations, risks, and blockers plainly, and do not add comments, docstrings, type annotations, or impossible-case error handling to untouched code.

## Definition Of Done
- Automated test surfaced for review before implementation (or no-test rationale stated), superseded tests and fixtures are removed, and relevant tests, lint, format, type-check, static analysis, and build pass.
- No debug statements, hardcoded secrets, or commented-out code; docs match behaviour; rollback risk is understood before schema, config, or generated-output changes.

## Breach Protocol
- On rule breach, stop immediately, acknowledge plainly, and re-offer options only: `Contract breach. Stop. Re-offer options only.`
